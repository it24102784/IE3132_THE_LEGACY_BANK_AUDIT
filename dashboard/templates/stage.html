How to play

  1. Open the bundled network-tools terminal with docker compose exec kali_player bash — this whole stage is played there, not in your browser.
  2. You are given a network range: 10.10.10.0/24. Your first job is to find which machines are alive on it.
  3. For each live machine, find out which ports are open and what services are running on them.
  4. If you find a web service, inspect the full HTTP response, including the parts your browser does not show you.
  5. When you find something that looks like a flag (format LB{...}), come back here and submit it below.

Starting position

From the project folder, open the bundled attacker terminal and connect to the server. At the password prompt, enter the credential recovered in Stage 3; it is also shown on the Stage 4 success page. 

docker compose exec kali_player bash
ssh vaultadmin@10.10.10.10

How to approach it

  1. Check your access. Run whoami and id to confirm you are a low-privilege user. You will not need sudo for this challenge.
  2. Look for scheduled jobs. Check the system crontab, the cron drop-in directory, and your own crontab. 
    cat /etc/crontab
ls -la /etc/cron.d
crontab -l
    Look for an entry that runs as root. An empty user crontab is normal.
  3. Follow the job. Read its entry and inspect the script named there. Note what the script runs and which files or directories it uses. 
    cat <script-path-from-job>
  4. Compare permissions. Check whether your account can modify a script that is run by root. 
    ls -l <script-path-from-job>
  5. Search nearby. List the directory containing the script and inspect its neighboring files for the guarded clue. Submit the LB{...} flag you find to unlock Stage 6.
{% endif %} {% if stage.id == 6 %}

Escalation strategy

Continue from the low-privilege SSH account you used in Stage 5. If you closed that session, reconnect from the project folder: 

docker compose exec kali_player bash
ssh vaultadmin@10.10.10.10
  1. Confirm you are still the low-privilege user, then revisit the scheduled job and script you identified in Stage 5.
  2. Verify which account runs the job and whether your account can modify its script. Think about the consequence of root executing content you can change.
  3. Use a harmless test to confirm the scheduled script can perform an action with root privileges. Wait for the job's next run and check the result.
  4. Apply the same idea to make the protected flag readable from your account, then submit it here.
